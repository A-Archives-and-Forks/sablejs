## Baseline facts

These facts pin down where the remaining cost actually is, and correct one earlier assumption:

- **Arithmetic already compiles to native JavaScript operators.** The stack-to-local codegen's direct path lowers `MUL/DIV/MOD/ADD/SUB/SHL/…/BITAND/BITXOR/BITOR`, comparisons, `TYPEOF/POS/NEG/BITNOT/LOGNOT/INC/DEC`, and `POSTINC/POSTDEC` through `NATIVE_BINARY_OPERATORS` / `NATIVE_UNARY_EXPRESSIONS` in `src/codegen/index.js` — in both straight-line and structured scopes (both route through `emitStackToLocalRange`). The runtime helpers for these ops (`$r.add`, …) are only reached by scopes that fall back to `callForInstruction`. A "guarded numeric specialization" for arithmetic is therefore already in effect; the remaining numeric lever is local promotion (item 6), which subsumes the roadmap's "numeric-local specialization".
- **The measured sandbox tax is concentrated** (per `docs/performance.md`, boundary profile): write-guard resolution (`writeTarget`, 65M–108M/run on NavierStokes/Crypto), guest-call dispatch (`boundary.call`, 19M–37M/run on Richards/DeltaBlue), and host-intrinsic calls plus prototype-sensitive reads (RayTrace). Items 1 and 2 attack the first two directly.
- **`writeTarget` is exactly** `count + (value === functionConstructor → throw) + wrapperTargets.get(value) || value + (isObject && protectedValues.has → throw)` (`src/runtime/security.js`). Its no-op condition is therefore precisely characterizable, which item 1b exploits.
- **The guest branch of `boundary.call` is** `guestFunctions.has(callable)` → `pendingGuestEntries` save/increment/restore around `REFLECT_APPLY`. The compiled wrapper itself (fast-frame factory, `src/codegen/index.js` `generateFastFrameFactory`) already performs entry securing, sloppy `this` boxing, inline frame construction, and `currentFrame` save/restore. Item 2 removes only the dispatch around the wrapper.

The plan gate for this item said the `writeTargets` counter must drop on NavierStokes/Crypto; the measured write patterns show those two suites' hot writes flow through parameters and property-read chains (unmarked by design — see below), so the counter there is correctly flat. The drop is concentrated exactly where v2 aimed: `this`-targeted and `new`-result writes. The v1 pass (`src/backend/guest-provenance.js`) marks GETLOCAL outputs that provably hold guest-created objects, letting sandbox `SETPROP`/`SETPROP_S` skip `writeTarget` via `$setGuest`. Its coverage on the V8 suite is 36 one-time setup sites; the write-dominated suites' hot loops write `this`-targeted fields and `new` results. v2 closes those two gaps.

### 1a. `NEW`-result provenance (static)

**Mechanism (final form).** The slot/value state in `analyzeScope` now carries `{ marked, scopeId }`: `scopeId` pins a value to closures of exactly one scope (seeded at `CLOSURE` ops, AND-meet through SETLOCAL slots and phi joins). A `NEW` operation's output is marked iff its constructor input (`inputs[0]`, per the MIR lowering's `CALL`/`NEW` splice in `src/ir/mir.js`) is marked **and** its scopeId pin is non-null **and** that scope is return-safe. The mark flows through SETLOCAL slots and phi joins exactly as v1 does, and is written back as `instruction.guestObjectOutput = true` on both `GETLOCAL` and `NEW` instructions. Codegen's `NEW` case attaches a `guest-object` temporary origin when the mark is present, so `SETPROP`/`SETPROP_S` on `new` results select `$setGuest`.

**Return-safety.** A constructor scope is return-safe when it is lightweight and every live `RETURN`'s value producer is one of `THIS/UNDEF/NULL/TRUE/FALSE/INTEGER/NUMBER/STRING` (never an optimized producer, never a jump target — branch args plus every structured-region boundary offset, since a jump can land on a producer without executing it). Return-safe constructors always yield the fresh `new` object. The analysis runs after the last SSA pass, and the post-provenance peepholes (copy-folding, constant-branches, unreachable-code) only elide or retarget within the existing boundary set, so the verdict cannot go stale. A constructor with a single risky `RETURN` forfeits the mark entirely — deliberately coarse.

**Soundness.** `new` on a guest closure constructs a plain object whose prototype chain the closure controls; it is by construction never a wrapper, a capability token, or a protected intrinsic, so `writeTarget` is a provable no-op. If the constructor input is unmarked (it may be a wrapper or an unproven value), the output stays unmarked and the guarded path is preserved. Marked-value stability rules from v1 apply unchanged: `NEW` is not folded, not DCE'd, not copy-propagated.

**Explicitly excluded — `new Array(...)` and friends.** Standard intrinsic names are imported as globals via `OBJECT_DEFINE_PROPERTY` over `STANDARD_GLOBALS` at instance creation (`createGlobal`), so a host can inject a hostile constructor under the same name; a static mark would let a protected/mediated result take the unguarded write path. Writes to `new Array` results stay on the guarded path (pinned by test).

**Phase 2 — construct-only `THIS` provenance** (not yet implemented). If every use of a closure value in the whole program is a `NEW` callee input (a use-site escape check over the value graph — never a `CALL` callee, never stored to a property/global/returned), then within that scope `THIS` outputs are marked guest. This covers constructor bodies (`function Klass() { this.x = … }` invoked only via `new`); method-called scopes simply never qualify. With the frame stamp in place this is a smaller win than originally estimated — it only saves the flag read plus the per-call WeakMap probe for constructor bodies, not a per-write resolution.

### 1b. `this`-targeted writes: runtime frame stamping

Method-call hot loops (`task.run(p)` writing `this.field`) cannot be proven statically without interprocedural receiver provenance, so the receiver classification moves to runtime — computed **once per call** instead of once per write.

**Mechanism.**

1. **Boundary predicate (shipped).** `isUnmediatedWriteTarget(value)` in `security.js`, defined directly next to `writeTarget` as its exact no-op complement: `value !== this.functionConstructor && this.wrapperTargets.get(value) === undefined && !(isObject(value) && this.protectedValues.has(value))`. It performs no counter increment and never throws. A pinning unit test asserts the two cannot drift across a sweep of guest/host/primitive/protected values (with `Object.is`, since `===` is false for NaN): for any value, `isUnmediatedWriteTarget(v) === false` whenever `writeTarget(v)` would throw or return a target other than `v`.
2. **Scope analysis (codegen, shipped).** During emission, a scope that emits `SETPROP`/`SETPROP_S` whose object operand is a `THIS`-origin temporary (origin kind `this-value`, attached by the `THIS` case) sets `usesThisWrites` in its metadata. Only such scopes pay the per-call classification.
3. **Frame stamping (shipped).** After sloppy `this` boxing, when `metadata.usesThisWrites` and security is sandbox: `$f.thisIsGuest = $r.boundary.isUnmediatedWriteTarget($this)` — emitted in all three frame builders: the fast-frame factory literal and the leaf-frame factory literal (both can host sandbox `$setGuest` writes; `$setGuest($r, $f, …)` does not match the leaf-frame exclusion regex), and in `RuntimeInstance.createFrame` (the shared-frame path, which also covers scripts, eval frames, and `perScopeFactories === false`). The flag is engine-private: the frame object is never guest-observable, and `$this` here is the post-boxing value, so primitive boxes (fresh runtime-created objects) classify as unmediated, matching what `writeTarget` would have returned for them.
4. **Codegen selection (shipped).** `SETPROP`/`SETPROP_S` with a `this-value` object origin emit `$f.thisIsGuest ? $setGuest($r, $f, obj, key, value) : $setSandbox($r, …)`. Both branches are byte-identical on the value side (`secureValue` + strict/sloppy writer dispatch); the flag only selects whether target resolution runs.

**Soundness.** `isUnmediatedWriteTarget` is the exact complement of `writeTarget`'s no-op condition by construction (and pinned by test), so when the flag is true, `$setGuest` performs precisely what `$setSandbox` would have performed after `writeTarget` returned the object unchanged — including the throwing cases, which classify as false and stay on the guarded path. Host-initiated entries secure the receiver before boxing (`secureHostEntryValue`), so the classified value is always the post-entry value. Sloppy `this` boxing happens before classification, so the box is classified, not the raw receiver. Mid-call staleness is impossible: `protectedValues` is immutable after construction, `wrapperTargets` membership is monotone and any wrap of the receiver happens at entry (the value secured by `secureValue` is the value classified), and `functionConstructor` identity is fixed — so a receiver's classification cannot flip during the call it belongs to.

**Security regressions (shipped as tests).** `this`-targeted writes where `this` is (a) a wrapper, (b) a protected intrinsic (must still throw — `F.call(Math)` blocked at all levels), (c) a plain guest receiver (writable through the stamp path at all levels), plus the exact-complement pinning sweep and the `new Array` exclusion — all at O0/O1/O2/Os. writeTargets counting asserts the stamp really skips resolution (`Counter.prototype.inc` pattern: exactly 1 writeTarget remains for the unmarked prototype store).

**Expected effect (measured).** This-write-dominated workloads drop their per-write resolution to a boolean branch: Richards writes/call −82.7%, DeltaBlue −21.5% (see the status table above). Workloads whose writes flow through parameters or property-read chains (NavierStokes, Crypto) are unchanged by design — their receivers are unmarked values. Gate: `--profile-boundary` A/B with per-call ratios (absolute counters are calibration-noise-prone: the harness runs each benchmark ≥1000 ms, so counts scale with speed).

## Item 2 — Guest direct-call fast path

**Status: IMPLEMENTED (2026-08-23).** Shipped as arity-specialized dispatch: the codegen picks a callee-side variant by the call site's static argument count (`$applySandbox0`–`$applySandbox5`, generic `$applySandbox` above five args), and the guest fast path — WeakSet probe, entry accounting, and the invocation itself — runs in one helper with no per-call args-array allocation. Evidence: 153 unit tests green (5 new dispatch tests), security battery at all four optimization levels green, 2,000-case differential fuzz clean, size gate green. Interleaved A/B (three rounds alternating variants, medians): Richards **963 → 1024 (+6.3%)**, DeltaBlue **1034 → 1121 (+8.4%)**; RayTrace/Crypto/NavierStokes flat within noise (their dispatch tax is host-side or write-side, untouched by design). CPU-profile share of the guest dispatch dropped from ~10.3% (dispatch 5.8% + helper 4.5%) to a single merged frame.

**What was tried and measured before the shipped design.** The plan's original mechanism (static identity guard `callable === <closure temp>` on known-function callables) measured ≈0 coverage on Richards (12 of 21.9M calls; the hot callables come from `GETPROP`, whose provenance is `mediated`, so no binding is known at the call site). A per-site membership memo (value-keyed array on the boundary) was then built and measured as a **~20% regression** (Richards 944 → 761): microbenchmarked against `WeakSet.has`, every array layout — holey, packed, two-array — costs ~15.7 ns/hit vs 8.4 ns for the native probe, so V8's inline-cached `WeakSet.has` is already the optimal membership test and a memo cannot beat it. The shipped win is not a faster membership test but the surrounding plumbing: (1) the guest branch of `boundary.call` was merged into the dispatch helper (one function call instead of two), and (2) guest calls no longer allocate the args array.

**Mechanism.** Generated `CALL` under `security: "sandbox"` emits the arity-matched helper directly:

```js
$applySandbox2($r, callable, thisValue, a, b)   // two-argument site
$applySandbox($r, callable, thisValue, [a, b, c, d, e, f])  // six+ args
```

Each `applySandboxValueN` dispatches exactly like the old `applySandboxValue`: `guestFunctions.has(callable)` → entry accounting (`calls`/`guestCalls` counters, `pendingGuestEntries` save/increment/restore in `try/finally`) → invoke; else the host `boundary.call` path (pure-intrinsic cache, code-constructor rejection, `wrapperTargets`, `protectedValues`) with a lazily built array, and the host-style `TypeError: X is not a function` for non-callables. The invocation itself is `FUNCTION_CALL.call(callable, thisValue, a0, …, aN)` where `FUNCTION_CALL` is `Function.prototype.call` captured at runtime-module load.

**Soundness.** `FUNCTION_CALL.call(callable, …)` is `Function.prototype.call` applied to the callable — semantically identical to `Reflect.apply(callable, thisValue, [args])` for plain ES5 closures, and it never reads `callable.call`, so guest code overwriting `.call`/`.apply` on a closure cannot hijack the fast path (regression test). The captured builtin is host state; guest code cannot reach it. Host callables (wrappers, raw intrinsics, proxies, unmediated functions) and non-function values take the same `boundary.call` path as before — dispatch classification is by the identical WeakSet probe, so nothing unmarked changes. Entry accounting is byte-identical to the pre-shipped guest branch, including exception paths. The wrapper prologue (entry securing, sloppy `this` boxing, frame build, `currentFrame` restore) is untouched and still runs. `FUNCTION_CALL.call` differs from `Reflect.apply` in no observable way for callables the probe admits (plain closures — ES5.1 has no callable proxies on the guest side; host functions route through `boundary.call`, which still uses `REFLECT_APPLY`).

**Security regressions.** Five new tests: emitted helper selection (arity variants vs generic array form at >5 args), correct results and `this` bindings for arities 0–6 at all four optimization levels, guest-overridden `.call`/`.apply` not hijacking the fast path, dispatch entry accounting parity (`calls`/`guestCalls`/`hostCalls`), and the host-style TypeError for non-function callables through every arity. Plus the pre-existing adversarial battery at all four levels and the 2,000-case differential smoke.

**Phase 2 (not shipped).** `NEW` with a known-function constructor origin (identity-guarded `$constructGuestClosure`) remains open; construction-heavy suites (RayTrace 2.8M constructs) route through `boundary.construct` unchanged. Its dispatch is a WeakSet probe + branch; the arity-array removal does not apply (construct arities are fixed per site too, but the measured construct dispatch cost is smaller than the call cost — revisit after Item 3).

## Item 3 — Object literal folding (INITPROP fast path)

**Status: IMPLEMENTED (2026-08-23).** Shipped as the `objectLiteralRanges` pre-scan in `emitStackToLocalRange` (sibling of `arrayLiteralRanges`): `NEWOBJECT + (STRING key, literal value, INITPROP)*` folds into one native object literal, and the emission loop skips the folded range. Evidence: 158 unit tests green (3 new: folded-literal semantics at all four levels, `__proto__` fallback, 3,000-entry size; plus 2 LICM frame-layout regression tests from the test262 follow-up), 3,000-case trusted differential fuzz clean, 2,000-case sandbox boundary fuzz clean, full test262 14,293/14,293 variants green (13,568 passed + 725 negative), size gate green. Interleaved A/B (five rounds, medians): Richards +1.1% / DeltaBlue flat — the V8 suites create few constant object literals (their objects come from `new X()` + field writes, not `INITPROP`), so the runtime win is unmeasurable there; the measurable win is code size: a 2,000-property data literal compiles to **27.9 KB instead of 205.6 KB of generated code (7.4×)**, the same class of win as the array analog (Kraken 47.6 MB → 1.8 MB). Keep for size/compat, no runtime regression measured.

**Mechanism.** `NEWOBJECT + (STRING key, literal value, INITPROP)*` chains fold into a native object literal `{ "k": v, … }`. Conditions: keys are `STRING` operands (never `__proto__`); values are literal ops (`INTEGER/NUMBER/STRING/TRUE/FALSE/NULL/UNDEF`) or `optimized` literal folds (`NEG` → `-0`, arithmetic constants at O1+); the fold stops cleanly at the first non-matching instruction, so getter/setter entries (`INITGETTER`/`INITSETTER`) and dynamic values keep the runtime path on the same fresh object, and nested object literals fold independently while the outer chain resumes via `initProperty`.

**Soundness.** The target is a fresh, unobserved `NEWOBJECT`, so `INITPROP` cannot hit setters or `__proto__` chaining; ES5 duplicate keys (last wins) match native literal semantics (verified: `dup: 1, dup: 2` folds to `{ "dup": 1, "dup": 2 }`, later wins); ES5.1 leaves enumeration order unspecified, and the native literal defines keys in the same source order as the `INITPROP` sequence. **`__proto__` keys are excluded from folding**: native literal syntax gives `__proto__` special prototype-setting meaning (V8 Annex B) while ES5.1 treats it as a plain property — the fold stops at the key and the runtime path preserves ES5.1 semantics (regression test pins `o.__proto__ === p` with `__proto__` as a plain key at all four levels; the same behavior holds at O0, confirming the fold introduces no deviation). `NaN`/`Infinity` values are global-property reads (`GETPROP_S`), not literals, so they never fold — semantically correct since the sandbox treats them as host state. Sandbox: values are literals, so nothing needs `secureValue`; the target is fresh, so `writeTarget` was already a no-op; the fold removes the mediation from `SANDBOX_MEDIATED_OPS` for exactly the cases where it was a no-op. Trusted mode gets the same win (native literal instead of the `initProperty` helper).

**Tests.** Three new: (1) folded-literal semantics — mixed values (int/string/bool/null/undefined/`-0`/1.5/duplicate keys), nested literal, `NaN`/`Infinity` fallback — at all four optimization levels against native V8 semantics, plus generated-code assertions that the constant chain emits one literal and only `NaN`/`Infinity`/`nested` keep the runtime path; (2) `__proto__` fallback at all four levels (plain-property ES5.1 semantics, no `"__proto__":` literal in output); (3) 3,000-property data literal compiles under 200 KB of generated code. Plus 3,000-case trusted differential fuzz and 2,000-case sandbox boundary fuzz. **Infra fix during validation:** the boundary generator could emit unbounded f0↔f1 mutual recursion, which stalls the QuickJS wasm oracle for minutes (wasm stack exhaustion surfaces slowly); guest callables are now restricted per function so the call graph is acyclic (f0→f1→∅, main→both) — the 2,000-case campaign runs in ~25 s on any seed.

**Expected effect (measured).** Literal-heavy code removes per-property helper round-trips: a 2,000-property data literal compiles to **27.9 KB vs 205.6 KB generated code (7.4×)**; compile time is flat (95.6 ms vs 97.1 ms); the V8 suite is flat within noise (Richards +1.1%, DeltaBlue ±0% over five interleaved rounds) because the suites' objects come from `new X()` + field writes rather than constant literals — the win concentrates on real-world data literals (config objects, tables, JSON-like payloads), the same class of win the array analog already proved on Kraken imaging (47.6 MB → 1.8 MB per test). Gate: `benchmark:size` green.

## Item 4 — Strict-mode parameter propagation

**Mechanism.** `canPropagateLocal` in `src/backend/mir-optimizations.js` currently excludes all parameter slots because sloppy `arguments` can alias them. Relax to include parameters when `scope.strict`: the GETLOCAL form already proves the slot is not closure-captured (captured slots use GETLOCAL2), and in strict mode `arguments` is unmapped and `fn.arguments`/`fn.caller` are poison-pill accessors, so no aliasing path for parameters exists. One predicate change unlocks copy propagation, GVN, and LICM on parameters in strict scopes.

**Soundness.** Sloppy scopes keep the exact current predicate (unchanged behavior). Strict `arguments` is an unmapped snapshot by the ES5.1 spec, and the runtime's strict capture does not install mapped accessors. The same condition later gates parameter promotion in item 6.

**Why it matters.** The recommended deployment path is Babel/SWC → ES5.1 → sablejs, and downleveled output is always strict — this is the highest real-world-coverage change per line of code in this plan.

**Tests.** Strict function with parameter loads in a loop (LICM hoist observed), cross-block GVN reuse on a parameter, copy propagation of literals into parameter slots; sloppy `arguments` aliasing regression (`arguments[0] = x` observable through the parameter, `fn.arguments` mapping) must stay byte-identical. Differential smoke at all levels.

## Item 5 — Intrinsic-read LICM (RayTrace lever) — VALIDATED OUT (2026-08-23)

**Mechanism.** Extend the loop-invariance machinery from private locals to `GETPROP_S` reads on protected-intrinsic bindings. Codegen marks the `GETVAR`-by-name path for names in the protected-intrinsic binding list (`Math`, `JSON`, …) with a `protected-global` temporary origin when the name is not a declared local (the `variableKind` resolution already distinguishes this); a `GETPROP_S` whose receiver origin is `protected-global` becomes LICM-eligible exactly like a private local load. The hoisted `const` holds the mediated read result.

**Soundness.** Under the sandbox contract the host may not extend intrinsic prototypes after the first instance, and guest writes to protected intrinsics throw (`assertMutable`), so the read — and its result identity — is loop-invariant: `wrapHostFunction` dedups wrappers per target, so the hoisted wrapper is the same object every iteration. Shadowing is excluded structurally (`var Math` in a guest scope resolves to the local path and never receives the origin; with/eval scopes are non-lightweight and already excluded from LICM). The protected-binding list must be generated from the same source as the runtime's protected-intrinsic graph or pinned by a startup assertion, so the two cannot drift.

**Validation-first — verdict: drop.** `--profile-boundary` with a per-name `boundary.get` histogram shows RayTrace's 2.54M mediated gets are **guest prototype-chain reads, not intrinsic reads**: `prototype` 1.27M (the `Vector.prototype.subtract.call(…)` ES5 idiom — `prototype` is a sensitive name, always mediated) plus the chained method keys `subtract`/`multiplyScalar`/`add`/`blend`/`multiply`/`addScalar` 1.27M (mediated via the chained-off-mediated origin rule). Zero `Math`/`JSON`-type keys appear. DeltaBlue's 162K mediated gets are the same shape (`prototype`/`call`/guest methods). The planned pass would drop the counter by ~0 — it fails its own gate. The real lever (hoisting `Foo.prototype.method` chains) is unsound without guest-write observation: guest code can reassign its own prototypes (sandbox allows guest→guest writes), so the chain is not invariant across calls in the loop. Filed as future work: prototype-chain method-call fast path behind a write-observation mechanism. Item 6's local promotion is the next lever.

## Item 6 — Local promotion (frame-shape specialization) — SHIPPED Phase 1 + Phase 2 + Phase 3 (2026-08-23)

**Mechanism (as built).** Promote locals of frame-layout scopes out of the `$f.locals` array into real `$exec` prologue variables (`let $p<scope>_<index>;`). The promoted slot **keeps its dead `void 0` placeholder** in the locals array — no index remapping, so every frame constructor, the `$getArguments` parameter mapping, and the metadata layout stay untouched; only `GETLOCAL`/`SETLOCAL` (and LICM hoists) divert to the variable. No selection heuristic: every eligible slot of an eligible scope is promoted (V8's register allocation handles cold slots; the loop-depth × access-count filter measured unnecessary). Eligibility (since Phase 3): O2/Os && non-script && direct variable scope (no with/eval/catch chain, own or inherited) && no `dynamicFunctions` && no `CLOSURE`/`GETLOCAL2`/`SETLOCAL2` ops — **there is no security term**. Phase 1 promotes `index > parameterCount`, Phase 2 additionally promotes parameters (`index >= 1`) in **strict** scopes. Promoted parameters are initialized in the declaration (`let $p1_1 = $f.callArgs[0], …`) — `$exec` only receives `($r, $f)`, while `$args` lives in the enclosing factory closures; the frame literal still fills the (dead) slot for constructors and the arguments mapping.

**Frontend invariant behind the eligibility.** Every exclusion term is structurally unreachable in the scopes LICM can reach: a `CLOSURE` op marks its scope non-lightweight at the emission site (frontend `emitFunction`), the `Function` constructor (the only `dynamicFunctions` source) likewise marks the scope non-lightweight, and `GETLOCAL2`/`SETLOCAL2` are never emitted into HIR at all. So every lightweight, direct-chain scope with a loop is promotion-eligible, and the LICM mirror's skip covers the entire hoist space: under Phase 3 the `$h = $l[...]` hoist render for private locals is structurally dead (the mirror and the terms in the plan remain as defense-in-depth for future frontend changes).

**Soundness.** A scope with no `CLOSURE` op creates no nested closure, so no other frame's environment chain can ever contain this scope's environment node — the locals array is unreachable by the runtime name-walk (`findBinding`/`getVar`/`setVar`/`hasVar`) and by captured reads from any descendant (there are none). `$apply`/`$r.call` invoke the callee with its creation-time chain; `dynamicFunction` uses a null chain; `hardenFastFrameChain` touches only stack/references; inline plans read only parameters. **Strict parameters (Phase 2)** add one runtime path to check — the `arguments` object — and it is safe by construction: `createArgumentsObject` builds its `frame.locals`-reading mapped proxy **only for sloppy frames** (the parameter map loop is gated on `!metadata.strict`); strict frames get a plain host Arguments object whose values come from `callArgs`, and `fn.arguments`/`fn.caller` are PoisonPill accessors that throw. Writes to a strict `arguments` are unmapped and never reach locals, so both aliasing directions (param → arguments, arguments → param) are exactly ES5 unmapped semantics. Sloppy parameters stay on the live array (the mapped proxy reads them through `frame.locals`). The optimizer already treated strict parameters as private (`canPropagateLocal`), so Phase 2 aligns the codegen with the analysis. A post-generation assertion fails loudly if a name-walk or environment-chain helper ever appears in a promoted scope. **Phase 3 (sandbox):** the eligibility has no security term because a boundary review found no sandbox path that observes `frame.locals` — the boundary helpers (`secureValue`/`writeTarget`/`isUnmediatedWriteTarget`) operate on values, never on frames; the only `frame.locals` readers besides `getLocal`/`writeLocalValue`/`deleteLocal` are the `evalFrame` branches, which target the eval caller (a scope carrying the excluded `EVAL` op). Phase 1's "trusted only" gate was a staging decision, not a soundness boundary. **Mixed-path demotion:** a stack-height mismatch (e.g. a constant-folded ternary merge) sends `GETLOCAL`/`SETLOCAL`/`DELLOCAL` through the runtime helpers, which read and write the locals array — the dead placeholder for a promoted slot. Codegen detects exactly the affected slots in the generated code (the scan covers `getLocal`/`setLocal`/`deleteLocal`) and demotes them (back onto the live array), regenerating the scope; emission is deterministic, so this converges in one retry. The LICM pass mirrors the eligibility predicate (including strict parameters since Phase 2) and skips hoists for promoted slots (a `$h = $p...` alias is pure redundancy).

### Item 7a — Dead-store elimination — SHIPPED (2026-08-23)

**Mechanism (as built).** Per-slot backward must-use liveness over the MIR CFG (O2/Os). For each propagable slot (`canPropagateLocal`: lightweight non-script scope, non-parameter index or strict-mode parameter — the same eligibility as copy propagation, widened by item 4), a fixpoint computes `liveIn`/`liveOut` per block (keyed by `block.start`, since successors are block START OFFSETS and loop headers/backedges are blocks too). Backward transfer per block: live at a position = live after the block (OR of successors' liveIn) plus any real read after the position; a store satisfies earlier needs and kills them. After the fixpoint stabilizes, every store at a dead position is marked `instruction.elided = true` and the codegen skips it. Because `SETLOCAL` in this stack-machine codegen is a stack PEEK (it copies the top of stack into the slot without consuming it), the elision leaves the stack schedule untouched — no drop-inputs are needed, unlike DCE's POP chains; the producer's stack traffic stays exactly where it was. Runs after every value-moving pass (copy-prop, LICM, GVN, local-CSE) and before the final SSA DCE, so the provenance marks written later cannot go stale.

**Which reads keep a store live (the optimized-read table).** Earlier passes rewrite loads and mark them on the HIR; DSE must classify each mark's runtime behavior, because codegen falls back to a real slot read in some cases:

- `literal` (copy-prop/peephole) — rendered as a folded literal, never touches the slot → **no-op for liveness** (does not consume, does not kill).
- `duplicate` (local-CSE) — stack-top copy of an adjacent load; the load itself is a real read DSE sees → **no-op**.
- `licm` (hoisted loop load) — rendered as `$h{scope}_{offset}`; the hoisted load IS a real read that DSE sees → **no-op**.
- `reuse` (GVN) — rendered from a temporary keyed to the *source* load's offset; the source may be elided by a later peephole pass, and codegen then falls back to a real slot read (`direct()` returns false when `instructionTemporaries.get(sourceOffset)` is missing) → **a consuming read**. This is free: no store can sit between a reuse and its dominating source (any store kills GVN availability), so the source load's own read already keeps exactly those stores live — treating `reuse` as a read cannot lose an elision.
- `DELLOCAL` is a **no-op**, not a kill: `deleteLocal` pushes `false` for lightweight frames without touching the slot (`src/runtime/index.js`), so a later read still observes the stored value. (The original implementation treated it as a kill and mis-elided the store in `var x = 1; delete x; return x;` — value 1 is correct in ES5 sloppy mode, since `delete` of a declared var is a no-op that returns false.)
- Unmarked reads consume the slot. The access filter gates on the op name FIRST, because other ops' first argument (NUMBER immediates, jump targets) can numerically collide with a slot index.

**Soundness.** Liveness is a sound over-approximation of future reads in both directions: an elided store has no read on any path before the next store (the `isRead` no-op classification above is the only judgment call, and each entry is derived from a render-path proof plus the codegen fallback rule), and every store that is kept is kept because a real read can observe it. Optimized reads are the subtle part: a `reuse`-marked read whose source later elides compiles to a **real slot read**, so treating it as a no-op would mis-elide the store feeding it (found by differential fuzz, seed 939: GVN marked a loop read `reuse` → its source was copy-fold-elided → codegen fell back to `getLocal` on a DSE-deleted slot → `undefined[1]` TypeError). Similarly, treating `literal`/`duplicate`/`licm` reads as kills was unsound in the other direction — a folded read between a store and a later live read killed the liveness that should have kept the store (found by the unit suite: a `first = stable` copy-fold between `stable = 7` and a return-block read mis-elided the store, `NaN`). The named-function self-binding prologue (`CURRENT SETLOCAL[nameSlot] POP`) is elided when the name is never read; codegen's inline-plan prologue strip recognizes the resulting `CURRENT POP` pair with an elided SETLOCAL between them (elided ⇒ no self-read — a real read would have kept the store live). Scopes with a dynamic chain (`hasDynamicChain`: with/eval/catch ops, own or inherited — the same gate as LICM and the codegen's frame layout) are skipped wholesale: the desugared empty catch of every try/finally emits a CATCH op, so a try body's stores can be read on the exception path (handler/finally/continuation), which the MIR CFG has no edge for (a THROW block has no successors), and the runtime name-walk can reach the frame's env node from a nested catch scope — both reads are invisible to op-level liveness. Frame-layout scopes can contain none of these, so eliding their dead stores stays unobservable. (Found by test262 S12.14_A15: `try { result += 2; throw "ex" } finally { break }` — the finally's break path reads `result` after the throw, and the mis-elided store turned 2 into 0.)

**Gates (all green).** 178/178 unit tests (13 new DSE tests: store-store chains, the copy-fold-gap regression, delete-noop semantics, sloppy-param exclusion / strict-param inclusion, cross-block live and dead paths, orphaned-and-loop-dead stores, loop-carried liveness, slot-index vs immediate collisions, the reuse-dangling-source regression, with-env exclusion, the try/finally exception-path regression, kill-switch off); test262 14,293/14,293 variants (13,568 passed + 725 negative), 0 failed; differential fuzz at seeds 1 (5,000 cases) + 7 (5,000, re-run on the fixed code) trusted + 3,000-case sandbox variant + 3,000-case boundary fuzz, all clean; e2e build+node; `size --check` within budget.

### Item 7b — Dense `JCASE` → native `switch` — SHIPPED (2026-08-23)

**Mechanism (as built).** For each structured `Switch` region, the codegen first checks whether every non-default case test is a single compile-time constant: the test range `[testStart, branch)` (the instructions between the test expression and its `JCASE`) must hold exactly one non-elided instruction that produces a constant — `INTEGER`/`NUMBER`/`STRING` (value in `args[0]`), `TRUE`/`FALSE`/`NULL`/`UNDEF` (value in the op name), or a constant-folded op (`optimized.literal`). When all tests qualify, the labels are de-duplicated with a `Set` (SameValueZero, so −0/0 and NaN/NaN collide), there are ≥ 2 constant cases, and the stack-to-local emitter is enabled (`context.enabled`, i.e. O2/Os — O0/O1 have no `$s` alias and every op is a runtime call), the region takes the dense path: the discriminant range is emitted normally (its final unconditional flush materializes the value on `$s`), then `const $d<id> = $s.pop();` captures it and `$switch<id>: switch ($d<id>) { case <literal>: … default: … }` dispatches. The `$switch<id>` label is kept because guest `break`s inside case bodies lower to `break $switch<id>` (`emitControlExit`). Case bodies are emitted with the exact same `emitRange` calls and order as the generic path, so fallthrough chains, nested regions inside bodies, and loop exits are bit-identical; only the header and the per-case guard chain differ. The kill switch is `denseSwitch: false` / `--no-dense-switch`. Stats: `codegen.stackToLocal.denseSwitches` / `denseSwitchCases`.

**Why it is sound.** ES5.1 switch semantics are: evaluate the discriminant once, then evaluate the case tests in order, compare each with strict equality (`===`, no coercion), take the first match (or `default`), skipping the remaining tests after a match. A native `switch` over the already-evaluated discriminant implements exactly this: labels compare with `===` in source order, first match wins, `default` runs when nothing matched. The generic path's `selector === -1` guard chain exists only because case test *expressions* may have side effects and must stop being evaluated after a match; constant tests have no side effects, so the guard is vacuous and dropping the test evaluation is unobservable. SameValueZero-distinct labels can never both match the same discriminant — `NaN === x` is false for every `x` (a lone NaN label never fires, same as the generic chain), and any other `===` match fixes the discriminant to the label's exact value (`-0` and `0` both match both labels, which is exactly why that pair is rejected) — so first-match order coincides with the chain. Duplicates (valid guest code, first match wins) would be a host `SyntaxError` and are rejected by the SameValueZero check, falling back to the chain. The discriminant is consumed exactly once on every path (generic: `$r.caseJump` on match or `$r.pop` on no-match; dense: the single `$s.pop`), so the guest stack is identical. Case tests that are unreachable (`branch.unreachable`) force the generic path — the generic chain never evaluates an unreachable test, but a native label would fire when the discriminant equals it, so dense must not guess. At O0/O1 there is no `$s`; at Os the `stackless` aliasing rule requires `$s` to be referenced exactly once, and the dense path's `$s.pop()` adds a reference, which keeps the alias (identical to the generic path's `branchValue`), so neither mode can reach dense unsoundly. Label rendering reuses `jsLiteral` (`void 0`, `NaN`, `-0` are all valid case labels), and `case void 0:` / `case NaN:` / `case -0:` are legal host syntax.

### Item 7c — Leaf-frame pooling — SHIPPED (2026-08-23)

**Mechanism (as built).** Every O2/Os leaf scope (stackless, lightweight, no closure capture, no runtime helper touching the frame — the `generateLeafFactory` inline-literal path) now gets a per-factory freelist: `let $poolHead = null;` in the factory closure, with pooled frames chained through a `poolNext` field on the frame object itself — no container, so no `Array.prototype` dependency (trusted-mode guest code can pollute `push`/indexed setters). The compiled callable's acquire path is `let $f = $poolHead; if ($f) { $poolHead = $f.poolNext; <slot rewrites>; $f.thisValue = $this; $f.callerFrame = $r.currentFrame; $f.callArgs = $args; } else { $f = { literal }; }` — the reuse path performs **zero allocations** (no frame, no locals array) and omits the per-factory-constant fields (`metadata`, `currentFunction`). The release path runs in the existing `finally`: `$r.currentFrame = $f.callerFrame;` then `if (!$f.argumentsInitialized) { $f.poolNext = $poolHead; $poolHead = $f; }`. The `argumentsInitialized` guard retires frames that materialized an arguments object: `createArgumentsProxy`/`getArgumentsValue` hold the frame and lazily map `frame.locals`, so reusing the frame would alias a different call's parameters — those frames never re-enter the pool. `thisIsGuest` (sandbox, receiver-writing scopes) is re-stamped on acquire because it is receiver-dependent.

**The read-set refinement (why the acquire rewrites only some slots).** The pooled frame's `locals` array is only ever read by the `$exec` body it serves: leaf frames are lightweight and stackless, so no runtime helper observes them (`getLocal`/`setLocal`/`findBinding` walk environment chains the frame does not participate in, and any `$r.<helper>($f` call would disqualify the scope from leaf), and arguments-materialized frames are retired. `computeLeafLocalsReads` scans the generated `$exec` body for `$l[index]` reads (via the `const $l = $f.locals` alias; a write is `$l[i]` immediately followed by `=`), and the acquire rewrites exactly those slots — which local promotion (item 6) makes parameter slots in practice (every `var` compiles to a real `$exec` variable; any slot that demoted to a runtime helper would disqualify the scope from leaf). This is what keeps the reused array on V8's packed-elements fast path: storing `void 0` into a double-representation array transitions it to generic elements, after which every double-valued local is boxed into a HeapNumber on each acquire (~8.6 ns/call measured as the difference). The first `void 0`-free acquire leaves a holey-double/holey-smi array untouched forever. Unclassifiable bodies (computed-index access, a bare reference to the array) return null and reset every slot — the safe superset. Measured on the V8 suite: 103 pooled scopes, 100 acquire resets, **zero `void 0` stores**.

**Why it is sound.** The frame is unreachable while pooled: leaf eligibility (`!code.includes("$f.environment")` and no `$r.*($f` helper) proves the body cannot leak it, `$f.line`/`$f.column` are write-only, and the freelist link lives on the frame. Re-entrancy is safe because release happens only in the `finally` after `$execute` returns, so a frame still active on the host stack (leaf → host callback → leaf) or in a recursive guest chain is never re-acquired — the pool grows to the maximum concurrent depth of each factory (recursion depth for `nz`/`dec` chains, 2 for the `inc`/`mix` storms). Receiver writes are covered by re-stamping `thisIsGuest`; caller-chain walks (`fn.caller`, `findActiveFrame`) see the rewritten `callerFrame`. `new` on a pooled leaf works through host `new` semantics (the callable is a plain function; a primitive return yields the fresh object). Stale slot values are unobservable by construction — the frame is unreachable between calls, and the acquire rewrites exactly the slots the body can read. The kill switch is `framePooling: false` / `--no-frame-pooling`; stats: `codegen.framePooledScopes`.

## Item 8 — NEW-dispatch arity specialization — SHIPPED (2026-08-23)

**Mechanism (as built).** The `NEW` case lowers to a helper matched to the call site's static argument count. Sandbox: arities 0–5 emit `$constructSandboxN($r, constructor, a0, …)`; the helper's first action is the boundary check `boundary.guestFunctions.has(constructor)`, and a guest constructor then builds directly with `new constructor(a0, a1, …)` — no args-array allocation, no `Reflect.construct` indirection, and none of the generic path's prologue re-authentication. Arity ≥ 6 or a non-guest constructor falls back to `constructSandboxValue(runtime, constructor, [args])`. Trusted: when the callee renders as a statically-addressable expression (identifier, dotted member chain, numeric-literal-index member chain — the `^[$A-Za-z_][\w$]*(\.[$A-Za-z_][\w$]*|\[\d+\])*$` regex), the codegen inlines a native `new ${constructor}(${args})`; anything else keeps `$construct(constructor, [args])`. The kill switch is `arityConstruct: false` / `--no-arity-construct`.

**Why it is sound.** The arity helper mirrors item 2's `applySandboxValueN` shape: the `guestFunctions` membership test is the entire boundary decision, and the `pendingGuestEntries` counter is incremented/decremented identically, so host re-entry detection is bit-identical to the generic path. A guest constructor invoked with already-secured stack values crosses no boundary — sandbox codegen's stack discipline guarantees the arguments are guest-secured — so passing them straight into `new` performs no skipped securing. Non-guest constructors (host functions, capability-injected globals) keep the full `constructSandboxValue` path, including its argument securing and guest-result marking. Trusted inline `new` is exactly `$construct`'s semantics for ES5 (no `new.target`, no `super`, no classes): `Reflect.construct(c, args)` with default `newTarget` ≡ `new c(...args)` for every ES5 constructor. The regex guard limits the inline to callee expressions that render without re-evaluation (a member chain with a runtime index could evaluate its base twice if inlined naively — numeric-literal indices can't), and every other callee keeps `$construct`, so evaluation order and count are unchanged. The generated call site marks the result with the same `guest-object` provenance when `instruction.guestObjectOutput` demands it, so downstream securing behaves exactly as before.

## Item 9 — Slot-provenance write stamps (per-store write classification)

**Status: IMPLEMENTED (2026-08-23).** Write-target resolution for property writes whose receiver is a frame local now runs once per store into the slot instead of once per write. Sandbox O2 only — Os keeps the size floor and trusted is untouched (the runtime path is identical at both securities; only the generated dispatch differs). This is the direct attack on the measured write-guard tax (65M–108M `writeTarget` resolutions per run on NavierStokes/Crypto): those suites' hot receivers flow through parameters and `var` slots, which the v1/v2 provenance marks (literals, `new` results, `this`) deliberately do not cover — the plan's item 1 status table called this out as the remaining write-side gap.

**Mechanism (as built).** In frame scopes (lightweight, direct-variable, stack-to-local on — the same isolation shape item 6 uses), codegen records which slots ever feed a property write: `GETLOCAL` emits a `guest-slot` temporary origin, and a `SETPROP`/`SETPROP_S` whose receiver carries it registers the slot in the scope's provenance plan (shared across regenerations via `options.provenanceSlotPlans`, so retries keep the same tracking). Every tracked slot gets a boolean stamp `$q<scopeId>_<index>` declared in the generated function prologue. `SETLOCAL` to a tracked slot reclassifies the stamp: values with static guest provenance (guest-object/closure/known-function origins) stamp `true`; everything else resolves at runtime with `$r.boundary.isUnmediatedWriteTarget(value)` — the exact no-op complement of `writeTarget`, evaluated **once per store instead of once per write**. A write site whose receiver comes from a tracked slot emits:

```js
($q === undefined ? $q = $r.boundary.isUnmediatedWriteTarget($o) : $q)
  ? $setGuest($r, $f, $o, key, value)
  : $setSandbox($r, $r.boundary, $o, key, value);
```

The lazy `=== undefined` fallback covers the store-before-discovery pattern (a write site emitted before any classified store — the stamp then initializes from the receiver itself, which is the value the slot holds at that point). Sloppy parameter slots get a prefix guard `!$f.argumentsInitialized &&`: the mapped arguments proxy can write `frame.locals` directly, bypassing `SETLOCAL` classification, so once arguments materialize the stamp may be stale and the write takes the full path. Non-parameter slots cannot be reached by the proxy (the map covers only parameter names — the `lastIndexOf` mapping that folds var-redeclared names into the same slot, which is exactly why the guard is name-based); strict scopes never get the guard (unmapped `arguments`, PoisonPill accessors). Stamp injection lands before the prologue, so parameter classifications read `$f.callArgs[i-1]` (promoted params) or `$f.locals[i]` (live slots) — never the `$l`/`$p` aliases (TDZ). A mixed-path `$r.setLocal($f, i)` on a tracked slot (the runtime helper writes the locals array without reclassification) permanently drops the slot from the plan and regenerates — the same convergence shape as promotion's demotion: the `dropped` set prevents re-adding, emission is deterministic, and the driver's loop bound (`attempts > initialCount + variables + 1`) is a backstop against an (unreachable) cycle. Kill switch: `slotProvenance: false` / `--no-slot-provenance`. Stats: `codegen.slotProvenance = { trackedScopes, trackedSlots, droppedSlots }`; the full-suite compile tracks 60 scopes / 84 slots (349 fast-frame scopes).

**Why it is sound.** A slot's stamp records the classification of the value it currently holds, and every slot mutation path is covered: `SETLOCAL` reclassifies; the runtime `$r.setLocal` path drops the slot (regenerated code never reads a dropped slot's stamp — its write sites render the full path); the arguments proxy can only write parameter-named slots and only after materialization, which the `argumentsInitialized` guard gates; `deleteLocal` on a lightweight frame is a no-op on the slot (pushes `false` without touching it, item 7a); and no with/eval/catch/closure can reach the frame's locals — lightweight ⟹ no `CLOSURE` ops ⟹ no descendant environment-chain links, the item-6 argument (a descendant chain can only form at a `CLOSURE` op, and with/eval scopes are non-lightweight by the frontend marker). JS values are immutable, so a stamp that classified the stored value correctly at store time still describes the receiver the write site reads. The stamp is the `writeTarget` no-op complement maintained by construction — same predicate, same monotone data (`protectedValues` immutable after construction, `wrapperTargets` monotone, `functionConstructor` fixed) — so `$setGuest` performs precisely what `$setSandbox` would have performed after `writeTarget` returned the target unchanged, including the throwing cases (they classify false and stay on the guarded path). The guard is emitted only for sloppy scopes with tracked parameter-named slots; every other tracked scope pays no guard.

## Item 10 — Inline guest-stamp write path (native set / slim writer)

**Status: IMPLEMENTED (2026-08-23).** The guest branch of a provenance-classified write site (item 9's `$q` stamp, item 1's `thisIsGuest` stamp, and the direct guest-object marks) emits the write inline instead of calling `$setGuest`, which paid three call layers per write — `setGuestPropertyValue` → `writePropertyValue` → the strict/sloppy writer. Sandbox O2 only, gated on `context.slotProvenance`; the kill switch is `inlineGuestWrites: false` / `--no-inline-guest-writes`. This is item 9's natural second half: the stamps proved `writeTarget` is a no-op per store, so the per-write resolution was already gone — what remained was the helper-call tax on every classified write.

**Mechanism (as built).** The guest arm of the write-site ternary becomes, for a strict scope, a native `$o[$k] = $v` — `writeStrictPropertyValue` minus its `isIndexedPrototype` guard, which is provably dead on this path: the guard fires only for the host `Array.prototype`/`Object.prototype`, both protected intrinsics, and `isUnmediatedWriteTarget` classifies protected intrinsics `false`, so a guest-classified receiver can never be one (the classification is monotone — `protectedValues` is immutable after construction). For a sloppy scope the arm is one call to the captured non-strict writer `$writeSloppy` — silent-failure semantics must survive even though the generated module is strict, so a native set (which would throw) is never used there. Value-side securing is preserved verbatim (`typeof $v === "function" ? $r.boundary.secureValue($v) : $v` — the write path gates only on functions; the ambient branch is unreachable from it), and values whose static op proves primitive (`PRIMITIVE_RESULT_OPS`, mirroring `valueTypeForOperation`'s primitive outputs plus `ADD`) skip the probe entirely. **Purity gate:** the value render must be side-effect-free and order-independent — a named temporary with a recorded producing instruction, a promoted/hoisted local (`$p`/`$h`), or a literal — so the probe-and-write double evaluation can never re-run an effect. Call results, `$s.pop()` renders, and inline expressions are not pure and keep the `$setGuest` call. The temp→instruction recording for the purity check is deliberately separate from `instructionTemporaries`: the arithmetic/literal paths record into `temporaryInstructions` (via `recordWriteTemp`) without touching the "reuse" optimization's map, so enabling inline writes never changes reuse behavior.

**Receiver gating (the soundness line).** The inline form is emitted only where the *receiver* is provably guest — the `$q`-stamp ternary's true branch, `$f.thisIsGuest`'s true branch, and direct guest-object origins. Any other receiver keeps the full `$setSandbox` path; `writeTarget` resolution is exactly what blocks `Math.polluted = 1`-shaped writes to protected intrinsics, and the value-purity check must never substitute for it. (The first wiring made exactly this mistake — inlining into the unknown-receiver branch because the *value* was a pure literal — and the existing P0 proxy-trap test, which writes `Math.polluted = 1` from inside a guest proxy `set` trap, caught it as `'value' != 'throw'`. ## Item 11 — Literal-init fast path (own data properties without defineData) — SHIPPED (2026-08-23)

**Status: IMPLEMENTED (2026-08-23).** Object and array literals with non-constant values (`{count: 0, sum: 0, max: event.at}`, arrays with object elements) compile to `NEWARRAY`/`NEWOBJECT` + one `INITPROP` per property, and every `INITPROP` called `defineData(object, key, value, true, true, true)` — an `Object.defineProperty`-equivalent with a per-property `dataDescriptor` allocation. CPU profiles of the literal-heavy workloads put defineData at 12–18% and dataDescriptor at 3–7% — the largest shared cost across the workload suite. The fast path replaces that call with a plain `object[key] = value` assignment.

**Mechanism (as built).** In `initProperty`, when the value is present, the key is not `__proto__`, and a new module-level `prototypeSetterUnsafe` flag is clear, the property writes with a plain assignment. The flag is monotone and process-global (like the pre-existing `indexedPrototypeUnsafe`): once set, every later literal init in the process takes the slow path. It is set when anything could make the assignment observe an inherited accessor:

- any accessor descriptor — an own `get` **or** `set` key; a getter-only accessor has no setter to call, and assignment through it throws in the strict runtime module — installed on `Array.prototype`/`Object.prototype` via `Object.defineProperty`/`Reflect.defineProperty`, `Object.defineProperties`, or `__defineGetter__`/`__defineSetter__`, tracked in `observePrototypeMutation` (runs at every guest call);
- a chain swap of either prototype via `Object.setPrototypeOf`/`Reflect.setPrototypeOf` or a `__proto__` write through the strict/sloppy property writers and `Reflect.set` — defensive on modern hosts, which make both prototypes immutable-prototype exotics (the writes throw, so the chain never changes); the hooks pin host parity and cover engine variance;
- a module-load scan of both prototypes' own descriptors, so a host that installed accessors before loading the runtime also disables the fast path.

The guard is deliberately conservative: any hit degrades to the old exact behavior. Sandboxed programs can never set the flag (the intrinsic graph is protected — every listed mutation hits `assertMutable` and throws), so sandbox runs stay on the fast path unconditionally.

**Why it is sound.** `INITPROP` fires only on freshly created literal objects (`NEWOBJECT`/`NEWARRAY` — the frontend emits it solely from object/array literal evaluation): extensible, no own accessors, chain exactly the built-in prototypes (or an isolated null-prototype array when `indexedPrototypeUnsafe`). For such an object, ES5.1 literal evaluation — DefineOwnProperty with a data descriptor — and plain assignment agree point-for-point: both create the own writable/enumerable/configurable data property, and on arrays both route index keys through `ArrayDefineOwnProperty` (identical length extension; the `EMPTY` hole case is unchanged). The only divergences are inherited accessors in the chain (assignment consults them — a setter runs, a getter-only accessor throws or silently fails; literal init must neither) and `__proto__` keys (Object.prototype's own host accessor would swap the prototype instead of creating the property). The key check and the flag cover exactly those, and the fast-path conditions are evaluated in the runtime's strict module — a divergence would crash loudly, not silently corrupt. Duplicate literal keys redefine the same fresh own property with identical attributes either way.

## Item 13 — Inline the literal-init (INITPROP) fast path on fresh guest objects — SHIPPED (2026-08-24)

**Status: SHIPPED (2026-08-24).** The clean pinned profile's top sandbox cost was `initProperty` (~25% of json-transform sandbox). For a fresh literal object the helper's remaining work is: `assertMutable` (a no-op — protected objects are realm intrinsics; a literal temp created mid-run can never be in `protectedValues`/`propertyTarget`), the EMPTY-hole length branch (unreachable from the model stack — `EMPTY` is pushed via `$r.pushEmpty`, which flushes, so a hole init never has all three operands pending), the `__proto__` key check (the key is a static literal — excluded below when it spells `__proto__`), the `prototypeSetterUnsafe` flag check (kept live via the `$prototypesHaveSetters` module import — a plain data property would go stale mid-run, and the generated `$r` is the runtime *instance*, not the module: a module getter read `undefined` and silently always-inlined; the trusted item-11 unit tests caught it), and the function-value securing (preserved via the `typeof` probe, skipped when the value's static op proves primitive — the same `PRIMITIVE_RESULT_OPS` classification as item 10).

**Emitted shape.** `if ($prototypesHaveSetters()) { $s.push(o, k, v); $r.initProperty($f); } else { o[k] = probe(v); }` — the fallback branch re-materializes the full unpopped operand stack so the helper sees exactly what the runtime path would. Eligibility (all three operands must be pending on the model stack): object temp origin `guest-object`, key temp's producing instruction STRING≠`"__proto__"`/INTEGER/NUMBER (folded-literal keys conservatively fall back), value probe `typeof v === "function" ? $r.boundary.secureValue(v) : v` in sandbox (identity for guest-created functions, so it costs one `typeof` per init), no probe in trusted (no boundary). Kill switch `inlineGuestInit: false`; O2 only (O0/O1/Os carry no inline forms).

**Why sound.** `INITPROP` is emitted only for object/array literals, whose target is always the `NEWARRAY`/`NEWOBJECT` temp immediately below — a fresh object, provably not in the protected-intrinsic graph, so skipping `assertMutable` changes nothing. ## Item 17 — Deep-fold nested literal chains (input-literal materialization) — SHIPPED (2026-08-24)

**Status: SHIPPED (2026-08-24).** The real-speed kill-switch decomposition (`w17-decompose`, json-transform sandbox — no-stack-to-local 18.5×, no-member-inline 2.77×, no-guest-init-inline 1.84× confirm the shipped items; host-inline / small-func-inline / runtime-stack / guard-init flat) identified the top addressable cost: **`$exec0` materializes the entire input literal on every `run()`**. Each `INITPROP` costs a `$prototypesHaveSetters()` guard call + a `typeof` probe + `secureValue` + a keyed store — repeated per run for a constant that never changes. The pre-item-17 shallow fold (item 3's array/object literal folding) folded only scalar-valued properties; nested object/array values kept the runtime path. json-transform: input materialization 54 µs → 17.5 µs per run, full op 174.9 µs → 113.0 µs.

**Mechanism.** The stack-to-local range pre-scan's `resolveLiteralChain` recurses into nested `NEWOBJECT`/`NEWARRAY` temp chains: an element/entry whose producing instruction is itself a literal-chain head resolves recursively (depth ≤ 8), and the whole subtree renders as one native literal. `foldExcluded` (reuse/LICM source offsets, `globalValueProducer` outputs) and the depth cap bound the fold to single-consumption, bounded-depth chains; the emission side pushes `temporary(arrayLiteral.source, instruction, { kind: "guest-object" })` and skips the folded instructions via `endIndex`. Kill switch `foldLiteralChains: false` / `--no-fold-literal-chains` reproduces the exact pre-item-17 shape (the shallow fold only); O2 only (the `context.foldLiteralChains` field is `options.optimization === "O2" && options.foldLiteralChains !== false`).

**Why it is sound (strictly more correct).** Native literal evaluation defines properties with DefineOwnProperty + a data descriptor, which never consults inherited accessors — so the deep-folded literal provably cannot trigger an `Object.prototype` setter, and the per-property `$prototypesHaveSetters()` guard that protects the assignment-based inline (item 13) is not merely redundant but structurally unnecessary. The fold is a strict refinement: the folded code path has strictly fewer observable points than the guarded inline. `__proto__` keys are never folded (Annex-B prototype-setting vs ES5.1 plain-property semantics — item 3's exclusion, carried forward). `foldExcluded` keeps every folded chain single-consumption (a value consumed elsewhere must stay a named temp), and the depth cap prevents runaway recursion on pathological nesting.

## Item 18 — Branch-test stack round-trip elimination — SHIPPED (2026-08-24)

**Status: SHIPPED (2026-08-24).** The `$exec` interp self-time decomposition (item 17's exit state) found the loop-condition pattern `$s.push($v1_9); if (!$s.pop()) break $loop0;` executing on every iteration of the json-transform hot row loop: the branch test is computed into a temp, pushed onto the guest stack, and immediately popped by the branch. The round-trip is pure overhead — the test already sits in a single in-scope temp, so the branch tests it directly.

**Mechanism.** Stack-to-local branch emitters arm `expectBranchTest` with the **end offset of the test range**; the final batch of that range (matched by offset — the last instruction's `end`, contiguous in HIR) records the pending test in `pendingBranchTest` instead of pushing it to `$s`, and the following `branchValue` tests the temp directly. Sound by construction: the branch is the only consumer of a test value (single-consumption); the push+pop are both skipped (height-neutral, and the item-15b runtime-stack mirror is untouched symmetrically); `!chunkOpen` keeps the temp's `const` in scope at the branch; `Os` is excluded (reusable `$t` temps are not scope-stable); O0/O1 never enable the emitter. All 10 branch sites are covered: loop conditions (While/For head, DoWhile backedge, ForIn), simple if/else, Conditional, Logical short-circuits, and the DoWhile continue re-test. Kill switch `deferBranchTest: false` / `--no-branch-test-deferral` reproduces the exact pre-item-18 round-trip shape.

**Soundness bug caught by the differential gate (recorded).** The first design armed a **boolean** consumed by "the final flush of the range" — but `emitRange`'s walker emits the test range in *batches* split at nested-region boundaries (a nested Conditional/Logical ends a batch early). The first sub-batch's final flush deferred its value into `pendingBranchTest`, and the nested region's own deferral then **clobbered** it — the value was never pushed anywhere, the stack lost an entry, and the `!==` operands shifted → ReferenceError/RangeError vs native TypeError on fuzz seeds 464/734 (deterministic, pre-fix A/B: 0 mismatches before the item, 2 after). Fixed by matching the armed **end offset** (a sub-batch ends before the armed offset → pushes normally; only the final batch of the armed range may defer) and clearing the flag whenever the armed range ends, deferral fired or not. ## Not planned (and why)

- **PRE.** GVN + LICM already cover the private-load subset that occurs in practice; general cross-block redundancy is rare in ES5 code, and property-read PRE is unsound under getters without runtime guards.
- **Loop unrolling / strength reduction.** V8's optimizing compiler performs both on the generated code; doing them at HIR level duplicates work and bloats artifacts.
- **Aggressive cross-block copy propagation / phi coalescing.** The stack-to-local codegen already renames via temporaries; inter-block value threading is bounded by region-stack visibility checks, and extending it has a poor complexity/risk ratio.
- **Full type inference with int32 hints (`| 0`).** Wrong semantics on overflow; the guard-based specialization pattern is the sound alternative, and arithmetic is already native (see baseline facts).
- **Sandbox-mode aggressive inlining.** Boundary semantics must hold per call. The existing inline plans exclude `usesArguments` scopes precisely because sloppy `arguments.callee.caller` makes inlined frames observable; broader inlining has poor risk/reward.
